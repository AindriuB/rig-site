    rig: generic actions for agentic workflows¶

    Status: phase 1 was released as 0.1.0. Phases 2 and 2.5 ship together as 0.3.0 and are described in phase-2.md and phase-2.5.md; workflows.md documents the workflow file. Phase 3 (views and trackers) ships as 0.4.0 and 0.5.0: 0.4.0 is built and is described in phase-3.md; rig tracker report is built in 0.5.0. Later phases are outlines, each planned separately before it is built.

    Direction. rig provides generic actions (tasks, findings, notes, workflow transitions, push, pull requests, CI waits, context briefs, config, login) that any loop can use, driven by any harness: Claude Code, other agent CLIs, CI or a person. It has no built-in lifecycle: a workflow file defines states, transitions and the gates that guard them. A review loop is one such workflow, owned by the project that runs it. The sections below that describe such a loop are the history of how rig started.

    rig is its own tool. It began as a subdirectory of an agent toolkit and moved here with its history in phase 1.5. Its callers use it only through the contract below.

    Why¶

    rig started as the mechanics of an agent review loop: plan → fanout → review → verify → record. In that loop, state and rules lived in prose and shell text:

    • State is markdown the model re-reads. Task state is parsed out of ## Review round N and ## Wave verified — <sha> sections, then confirmed with gh and git on every turn.
    • Rules are enforced by parsing shell. scripts/push-guard.sh decides whether a Bash command is a safe push by matching its text. A regex cannot understand bash: extending the guard to chained commands took four review rounds, each of which found another way to push to main, and was reverted.
    • It is tied to GitHub. gh is called from scripts/ci-wait.sh and from the status, wave, merged and handoff commands.
    • It does not scale past one developer. Sequential task numbers collide, and PLAN.md and HISTORY.md conflict on merge.

    rig is a small Go program that owns the mechanical parts: pushing, pull requests, CI waits and status now; tasks, findings and context later. A command that takes typed arguments can refuse a bad push by construction, where a guard has to recognise one in arbitrary shell.

    Decisions¶

    • Go, standard library where possible. One static binary, no runtime.
    • Forge adapters only. gh now, glab next. Git is called directly; there is no git abstraction to swap.
    • The forge is auto-detected from the origin remote's host. The layered config (rig config) overrides it, by the scope order rig config get reports (local, repo section, .claude/rig.json, global), then origin detection. A kind from a less specific scope never overrides a host from a more specific one; a host that names no known forge falls back to a less specific kind. Without a home directory forge selection treats the global layer as empty, but rig push still fails closed (exit 2): its policy may live in the global file.
    • rig holds a token only for a service with no CLI of its own. GitHub and GitLab stay with gh and glab: the adapters shell out to them and use whatever login the user already has, and rig login github|gitlab only hands over to gh auth login or glab auth login. For Jira, which has no such tool, rig login jira stores a token, in the OS keychain unless the user explicitly chooses --store file. No config key holds a token or an account; see phase-2.5.md.
    • No built-in workflow. States, transitions, gates, severities and task fields come from a workflow file; rig ships only a small basic one. What rig enforces whatever the workflow says is listed in phase-2.md.
    • Harness-neutral. The CLI with --json and exit codes, and later an MCP server, are the only surfaces. Nothing assumes Claude Code.
    • scripts/push-guard.sh is unchanged. It stays as the backstop for a raw git push. rig push is the allowed route; the guard is not extended.

    Architecture¶

    Three layers. Only adapters know a technology.

    ./
  cmd/rig/              commands: policy and output
  internal/forge/       port: Forge interface, PullRequest, Check
  internal/store/       port: Store interface (phase 2)
  internal/tracker/     port: Tracker interface (phase 3); adapters in
                        exec/, jira/, github/, gitlab/, fake/
  internal/forge/github adapter: runs `gh … --json`
  internal/forge/gitlab adapter: runs `glab`
  internal/forge/fake   adapter: in memory, for tests
  internal/git/         rev-parse, push, worktree list, merge-tree
  internal/proc/        shell-free, time-limited subprocess
  internal/config/      .claude/rig.json
    1. Commands (cmd/rig) hold policy and output. Text by default, --json for agents. A command never calls gh, glab or a store backend directly; it calls a port.
    2. Ports (internal/forge, internal/store) are interfaces in neutral types. Nothing in a port names GitHub or GitLab.
    3. Adapters implement a port for one technology. They translate that tool's JSON and vocabulary into the neutral types.

    Supporting packages:

    • internal/proc runs a subprocess from an argument vector with a deadline. It never builds a shell string, and it kills the child when the deadline passes.
    • internal/git wraps the handful of git calls rig needs.
    • internal/config reads the layered config (rig config); .claude/rig.json is still honoured, and the forge and the push prefixes come from it:
    Key Meaning Default
    forge github or gitlab detected from the origin host
    host forge host, for self-hosted instances the origin host
    pushPrefixes branch prefixes rig push may push ["task", "record"]

    Install with go install github.com/AindriuB/rig/cmd/rig@<tag>. A caller that installs rig for its users can pin a tag and check rig version against the minimum it needs.

    The contract between rig and its callers¶

    A caller talks to rig only through its commands, their exit codes and their --json output. It never imports rig's code or reads its files, and rig never reads the caller's. That is what lets rig live in another repository and be versioned on its own.

    rig version prints a semantic version (0.1.0 for phase 1, 0.3.0 with phases 2 and 2.5, 0.4.0 with the first part of phase 3) and exits 0. A new command, flag or JSON field raises the minor version. A change to anything in the tables below raises the major version.

    An unknown flag is always exit 2: rig never ignores an argument it does not understand. In the phase-2 commands, exit 1 means refused by a gate or the workflow with nothing written, and exit 2 covers usage errors, an unknown or ambiguous task, a bad workflow file, and store or git errors. The commands' flags and behaviour are described in phase-2.md and phase-2.5.md, and the workflow file in workflows.md. RIG_ACTOR names who acted and RIG_WORKFLOW the workflow to use. The commands that write the store (task new, edit, move, set, count, parent, link, unlink; finding add, set; note add; tracker pull, refresh, report) also take --actor <name>, or its alias --role <name>, which beats RIG_ACTOR and git's user.name for the actor stamped on the events; an empty or control-character value, or the two flags with different values, is exit 2 with nothing written, and every other command rejects them as unknown options (exit 2); RIG_JIRA_TOKEN overrides a stored Jira token at use time.

    Stable text output

    • rig pr wait, green: exactly one line, CI green: PR #<n> or CI green: run <id>. Red: CI red: … first, then the failed names, then at most 40 log lines after --- log tail ---. Errors go to stderr with the prefix ci-wait:.
    • rig pr list, and the pull request lines of rig status: #<n> <ci> <head> <title, at most 50 characters>, then conflict and draft when they apply.
    • rig push, on success: pushed <branch> to origin.
    • rig task start, on success, exactly four lines, with these paddings:
    WORKTREE: <worktree path>
BRANCH:   task/<slug>
BASE:     <base branch>
OWNS:     enforced from <task file path>

    The base is origin's default branch, else main, master, trunk or develop, else the current branch. The worktree is <worktrees.root>/<repository directory name>/<slug>. - rig task finish, on success: MERGED: <branch> @ <short sha> -> <base>, then REMOVED: <worktree>, or KEPT: <worktree> (<reason>) when the worktree could not be removed or the branch moved during the merge (its later commits are not merged, and the branch is kept).

    The kit-task marker. rig task start writes the file kit-task in the new worktree's own git directory (git rev-parse --absolute-git-dir there), where git never commits it. A caller that guards file ownership (the kit's owns-guard) reads it to find the task file. Its contract: one line, the path of the task file with forward slashes even on Windows, ending in a single LF, with no byte order mark. The path is absolute: rig finds the file in docs/plan/tasks of the main checkout or its enclosing workspace repository, or resolves --task-file against the working directory. If the file cannot be written, rig task start removes what it made and exits 2, so a worktree is never left without its marker.

    Stable JSON fields

    A pull request, from rig pr view --json and each element of rig pr list --json:

    Field Value
    number integer
    url, title, head, headSha, base strings
    state open, closed or merged
    draft boolean
    mergeable mergeable, conflicting or unknown
    mergeSha the merge commit; present only once merged
    ci red, running, green or none
    checks array of {name, state, url}; state is pass, fail, cancel, pending or skipped

    rig pr checks --json is {number, ci, checks} with the same meanings.

    rig status --json is {handoff, tasks, worktrees, prs, prsError}: handoff is {written, lines} or absent; tasks is an array of task file names without .md; each worktree is {path, branch, ahead, dirty}; prs holds pull requests as above; prsError is present when the forge could not be reached, and the rest of the output is still valid. It also has store, the view of the local store, which needs no network: {tasks, findings, error?}. tasks are the tasks not in a final state, in the order a task moves through the workflow. Each is {id, short, slug, title, state, parent?, external?}, where state is the effective state, parent is the parent's short id and external is {kind, key}; findings is {open, byTask}, with byTask mapping a task's short id to its open findings. error is set, and tasks empty, when the store could not be read.

    rig task start --json is {worktree, branch, base, taskFile}. rig task finish --json is {merged: {branch, sha, base}, kept?: {worktree, reason}, removed?}.

    Task JSON. The task printed by rig task show --json, rig task list --json and the other task commands gains parent (a task id; absent when there is none) and external (absent when the task is not linked):

    external field Value
    kind, key the tracker kind (jira, github, gitlab or exec) and the issue key
    host, project, url, type strings, each left out when empty; type is the tracker's own level label (epic, Sub-task)
    owned the rig fields the tracker owns
    syncedAt, rev when the task was last synced, and the tracker's revision of the issue then
    drift the owned fields whose local value differs from the last snapshot; [] when none

    rig task show --children --json is the task with a children array of tasks.

    Tracker JSON.

    • rig tracker pull --json is {items, skipped}; an item is {task, key, existing, parent, warnings}, where task is a task as above and parent is the short id of its parent task, or "".
    • rig tracker refresh --json is {tasks}; an entry is {task, key, status, changed, replaced, error?, warnings?}. status is unchanged, updated, gone or error; changed lists the fields that changed; replaced is a list of {field, lost} for each local edit the refresh overwrote.
    • rig tracker report --json is {task, key, status, comment, skipped?, dryRun?, warnings?}; status is {from, to} and comment is {kind, id}, each null when that part was not sent. With --dry-run nothing is sent: status has only to, and comment has no id but a body.
    • rig tracker show --json is the issue: {key, url, title, description, acceptance, priority, assignee, labels, type, status, parent, rev}.
    • rig tracker status --json is {kind, trusted, capabilities, login}; capabilities is {parent, children, types, search, comment, setStatus, levels} or null, and login is {ok, error?}. For a tracker that can check its configured project (Jira) there is also project, {key, exists, empty}, and the text output gains project: RIG ok, project: RIG not found or project: RIG ok (no issues yet); a missing project does not change the exit code. When the check fails with an error, project is {error} and the text output says project: not checked: <error>.

    Tracker report. rig tracker report sends a task's progress to the issue it is linked to (the task must be linked to an issue of the configured tracker, else exit 2). With neither --status nor --comment it is --status --comment state.

    • The status is the workflow's tracker.report.status entry for the task's effective state, sent with the tracker's set-status call. It is sent before the comment, so a refusal means nothing has left the machine. A tracker that cannot set a status (or cannot comment) gives a warning and the other part is still sent; an unsupported status is dropped before the skip check, so a repeat whose other part is skipped reports skipped.
    • The comment is one of three fixed templates, and nothing else of the task (title, body, fields) is ever sent:
    • pr: rig: pull request for task <short>: <url>. The URL comes from the forge, by the task's recorded pull request number.
    • state: rig: task <short> is now in state <state>.
    • summary: the state line, then Counters: <name>=<n>, ... (names sorted; left out when the task has none), then Pull request: <url> (left out when the task has none). If the forge read fails, the comment is sent without the Pull request: line and the run warns.
    • --include findings appends a blank line, Open findings: and one - <short> <severity> <summary> line per open finding (nothing when there are none). --include notes appends a blank line, Notes: and one - <kind>: <text> line per note, oldest first. Line breaks inside a summary or note are folded to a space.
    • Each real run that sends something writes one tracker-report event {kind, key, status?: {from, to, asked?}, comment?: {kind, id, digest}, at}, recording only what was sent; digest is the hex SHA-256 of the comment body, and the body itself is not stored. asked is the status name the report requested (to is the one the tracker reached, which may be spelled differently, as GitLab's open becomes opened). An older rig skips the kind.
    • A part is skipped when the latest earlier report for the same issue, written since the task's latest link event, sent the same thing: the status when the requested name equals its last sent asked or to (case and surrounding spaces ignored), the comment when the latest comment of the same kind has the same digest. Two report runs at once can both send: there is no lock. When every requested part is skipped nothing is sent, no event is written, and the output says skipped ("skipped": true in JSON). skipped means the repeat check dropped a part: when the tracker's capabilities alone empty the request, the run exits 0 with the warnings and the normal (or dry-run) line, and skipped is false.
    • --dry-run calls no tracker method that writes, and writes nothing; it prints status: <name> and comment (<kind>): followed by the exact body a real run would send, with the same skip rules and warnings applied (a tracker that cannot set a status or comment, or whose capabilities cannot be read).
    • It never writes planning fields. A comment that fails after the status was sent leaves the status recorded and exits 2; the next run sends the comment.

    Markdown format. --format markdown (alias --markdown) is stable like JSON: sections and fields are only added; removing or reordering one is a major change. --format json is the alias of --json. Two different formats, or an unknown one, are exit 2. Text output stays free-form. Every Markdown output is UTF-8 with LF line endings, one trailing newline, no ANSI codes, no wrapping, and times in RFC 3339 UTC. A field with no value is left out, and a single-line value has its line breaks turned into one space.

    • rig task show: # <title>, then a bullet block with these labels in this order, each only when it has a value: id, slug, state, recorded state, branch, pr, head, reason, parent, external, created, updated. Then H2 sections in this order: Body, Fields, Counters, Findings (with --findings), Notes (--notes), History (--history), Children (--children). Body, Fields and Counters are left out when empty; a requested section with nothing in it prints none. Body is a blockquote: line endings become LF and every line starts with > (an empty line is >). So a task body, which may come from a tracker, cannot open a heading, a fence or an HTML block of its own. Fields and Counters are - name: value lines sorted by name. A finding is - <short> [<severity>] <status>: <summary> (<path>); a note is - <time> [<kind>] <text>.
    • rig task list: # Tasks, then a bullet per task, - <short> [<state>] <title> (<slug>), followed by — <key> for a linked task and ← <parent short> for a task with a parent. No tasks prints none. --tree indents each child under its parent in place of the ←.
    • rig context: H2 sections named as the JSON sections[].name (Header, Body, Findings, Paths, Overlap, History, Commits); a section the budget hid is left out. Body is a blockquote as above and the others are - bullets. An omitted count is the line _… <n> more_. The Header has parent: and external: rows for a task that has them. The budget is counted against the Markdown's own bytes; text and JSON are counted as before.

    What rig push does and does not guarantee¶

    Any command line that starts rig push can only make a non-forced push of one local branch named <prefix>/<name> to the branch of the same name on origin. It cannot name main or any bare branch, a tag, a refspec, another remote, or a force or delete option. Exit 2 means git push never started.

    Two things sit outside that guarantee.

    • .claude/rig.json is the user's file. Its pushPrefixes decide which prefixes count, so whoever can write it can widen the pushes: to release/x, say, though still never to a bare branch, a tag or a force. In a bare layout the worktree's own files apply, as for rig config. An agent must not edit it. The project settings template makes any Edit or Write of .claude/rig.json, in the project or in a worktree below it, and any shell command that names rig.json, ask first (tests/rig-settings.bats pins those rules). A permission rule matches text, so this is a barrier, not a proof: a shell command can build the file name without spelling it, and two commands the template already allows can write and run a file (git log --output=<path> and rg --pre <program>). Narrowing those allow rules is a separate change.
    • Git's own configuration is not constrained. A pre-push hook, or remote.origin.receivepack, runs whatever it says during any push, and an agent can set either with git config. rig push runs the repository's hooks like any push does, so it does not close this. The raw git push origin task/<name> form the push guard allows has the same limit. Closing it would mean pushing with hooks disabled, which would also disable the hooks a project relies on; that trade has not been made.

    The forge port¶

    type Forge interface {
    ViewPR(ctx context.Context, ref string) (PullRequest, error)
    ListPRs(ctx context.Context, opts ListOptions) ([]PullRequest, error)
    CreatePR(ctx context.Context, in CreatePRInput) (PullRequest, error)
    Checks(ctx context.Context, pr int) ([]Check, error)
    WaitChecks(ctx context.Context, target WaitTarget) (WaitResult, error)
    FailedLogs(ctx context.Context, target WaitTarget, failed []Check) ([]LogLine, error)
}

type PullRequest struct {
    Number    int
    URL       string
    Title     string
    State     PRState   // open | closed | merged
    Draft     bool
    Head      string    // head branch
    HeadSHA   string
    Base      string
    Mergeable Mergeable // mergeable | conflicting | unknown
    Checks    []Check
}

type Check struct {
    Name  string
    State CheckState // pass | fail | cancel | pending | skipped
    URL   string
}

    WaitTarget is a pull request number or a CI run id. Later phases add Merge, Comment and Reviews.

    A pull request's overall CI state is derived from its checks in one place, in the port, so both adapters report it the same way: red if any check failed or was cancelled, else running if any is pending, else green if there is at least one check, else none.

    Phase 1 commands¶

    Command What it does Exit codes
    rig push <task-id\|branch> [--worktree <path>] Pushes one loop branch to origin 0 pushed, 1 rejected by the remote, 2 refused
    rig pr view\|list\|checks Prints neutral output from the forge 0, 2 on error
    rig pr open --head <branch> … Opens a pull request. Never pushes, and takes its body only from --body, never from a file 0, 2 on error
    rig pr wait <pr> or --run <id> Blocks until CI finishes 0 green, 1 red, 2 error or timeout
    rig status [--json] The session brief, worktrees and one line per open PR 0

    rig push is the security-relevant command. It resolves a task id to its branch (task/<id>-<slug>, the slug taken from docs/plan/tasks/<id>-*.md, the same lookup as derive_slug in scripts/_wt-common.sh). It then refuses, with exit 2 and without running git, anything that is not a plain branch name under a configured prefix: a refspec (a:b), a + prefix, a .. segment, a tag, any force or delete flag, and any unknown flag. What remains is run as git -C <worktree> push -u origin <branch>:<branch> — an argument vector, so there is nothing for a shell to reinterpret.

    rig pr wait keeps the contract of scripts/ci-wait.sh, so callers do not change: the same exit codes, CI green: PR #N as the only line when green, the failed checks and a 40-line log tail when red, and CI_WAIT_TIMEOUT (seconds, default 1800). ci-wait.sh becomes a wrapper that execs rig pr wait.

    rig status prints one line per open pull request in the format commands/status.md already uses: #N red|running|green|none branch title [conflict] [draft].

    Phase 1 is read-only on documents. State still comes from the existing docs/plan files, git and the forge.

    The store and workflows (phase 2)¶

    A store holds work in progress outside the code tree: one append-only event log per task under refs/rig/tasks/<ULID>, local to the clone unless the user opts in to sharing it. A task's state is a fold over its events. Which states exist, which transitions are allowed and which gates guard them come from a workflow file, not from rig. Tasks, findings and notes carry typed fields the workflow declares. phase-2.md has the format, the commands and the extension points.

    The state machine this section used to define (planned → implementing → reviewed → verified@sha → pr_open → ci_green → ready → merged) is now an example workflow file, shown in phase-2.md as the worked example.
